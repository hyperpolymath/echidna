== Echidna Corpus — N-dimensional, octad-shaped, cross-prover

The corpus subsystem (`+src/rust/corpus/+`) is an N-dimensional index
over named declarations across multiple proof assistants, designed to be
the substrate for design-search, MCTS priors, and the
`+suggest+`/`+learning+` agentic surfaces. It also emits VeriSim-shaped
8-modality octads so the same data round-trips through the
`+/api/v1/octads+` endpoint.

____
*For the design history* see
link:decisions/2026-04-28-corpus-and-design-search.adoc[`+docs/decisions/2026-04-28-corpus-and-design-search.adoc+`].
____

=== What it is

Walks a project tree, parses every `+*.agda+` / `+*.v+` / `+*.lean+` /
`+*.idr+` file with adapter-specific heuristics, and produces:

* A list of *modules* (`+ModuleEntry+`) with options, imports, and
back-references to their declarations.
* A list of *declarations* (`+CorpusEntry+`) with name, qualified name,
kind, statement, optional proof body, source line, forward dependencies,
and an `+AxiomUsage+` hazard flag set.
* Three indices: `+by_name+`, `+by_qualified+`, and *`+dependents+`*
(reverse-dep — the inverse of `+dependencies+`). Reverse-deps answer
"`what proofs would break if I change `+wf-<+`?`".
* A *per-entry metrics tensor* (`+EntryMetrics+`): size, connectivity,
shape (recursive vs structural), hazards, K-elimination risk, head-
symbol class.
* A *per-entry embedding* (`+Vec<f32>+`, default *256-dim* structural
n-gram hashing over the declaration's canonical type shape; the legacy
32-dim raw-text backend is still available, and a GNN backend is
pluggable via the `+Embedder+` trait).
* An *8-modality octad* (`+DeclarationOctad+`) form for VeriSim
compatibility — semantic / temporal / provenance / document / graph /
vector / tensor / spatial.

=== CLI

[source,bash]
----
# Build an index
echidna corpus ingest --root <project> --adapter <agda|coq|lean|idris2>

# Query by name (qualified, short, or substring)
echidna corpus query <pattern> [--deps] [--reverse-deps] [--reverse-closure]

# Cosine-similarity nearest neighbours
echidna corpus near "<query text>" [--top N]

# Cross-prover semantic-class lookup (synonym table)
echidna corpus crossquery <semantic-class>

# Cross-prover identity, keyed on the canonical type shape (no dictionary)
echidna corpus identity <pattern> [--skeleton] [--cross-only]

# Octad emit / round-trip
echidna corpus export-octads --index <X.json> --out <X.octads.jsonl>
echidna corpus import-octads --octads <X.octads.jsonl> --out <X.json>

# Stats
echidna corpus stats [--index <X.json>]
----

=== Programmatic surface — the multi-axis query DSL

[source,rust]
----
use echidna::corpus::{Corpus, DeclKind, query::SortKey};

let corpus = Corpus::load_json("data/corpus/echo-types.json")?;

// Recursive functions, axiom-free, sorted by similarity to a goal.
let hits = corpus.query()
    .where_kind(DeclKind::Function)
    .where_axiom_free()
    .where_recursive()
    .near_text("WellFounded _<_")
    .order_by(SortKey::Similarity)
    .limit(10)
    .run();

for hit in hits {
    println!(
        "{:.3}  {}  : {}",
        hit.similarity.unwrap_or(0.0),
        hit.entry.qualified,
        hit.entry.statement
    );
}
----

==== Filter axes

[width="100%",cols="50%,50%",options="header",]
|===
|Method |What
|`+where_kind(K)+` / `+where_kind_in(&[K, …])+` |Filter by `+DeclKind+`
(Function/Data/Record/Postulate/Module).

|`+where_axiom_free()+` |Exclude any hazard.

|`+where_no_hazards()+` |Exclude hazards but keep declared
`+Postulate+`s.

|`+where_recursive()+` / `+where_non_recursive()+` |Self-reference
detection from the proof body.

|`+where_structural()+` |Constructor-pattern shape detection.

|`+where_name_contains(s)+` / `+where_qualified_contains(s)+` |Substring
filter.

|`+where_head_symbol(s)+` |Exact match on the statement’s first
identifier.

|`+where_adapter(s)+` |Restrict to one prover.

|`+where_has_reverse_deps()+` |Non-leaf entries.

|`+where_custom(fn)+` |Escape hatch — closure over
`+(&Entry, &Metrics)+`.
|===

==== Similarity (Vector octad)

[cols=",",options="header",]
|===
|Method |What
|`+near_text("…")+` |Canonicalise the query, embed with `+StructuralEmbedder+` (256-dim), cosine-rank. A query written in one prover's syntax matches entries written in another's.
|`+near_vector(Vec<f32>)+` |Pre-computed embedding (e.g. from a GNN).
|===

`+SortKey::{Default, Similarity, StatementSize, ProofDepth, Fanin, Fanout}+`.

=== Octad shape

Each declaration becomes one `+DeclarationOctad+` with eight modalities
(see `+corpus/octad.rs+`):

[width="100%",cols="50%,50%",options="header",]
|===
|Modality |Carries
|`+semantic+` |adapter, kind, name, qualified, statement, proof
|`+document+` |searchable_text + aspect tags (incl. hazard tags)
|`+graph+` |depends_on + depended_on_by + cross_prover_id (name tail, legacy) + cross_prover_identity_key / cross_prover_skeleton_key / identity_scheme / canonical_type
|`+provenance+` |SHA-256 hash chain over (parent, event, ts, file, line)
|`+spatial+` |file path + line + adapter namespace
|`+temporal+` |version chain — content_hash per rung
|`+tensor+` |EntryMetrics serialised as `+HashMap<String, f64>+`
|`+vector+` |embedding (default 256-dim StructuralEmbedder)
|===

==== Cross-prover identity (E6 `+Graph+`)

There are three keys, in decreasing order of strength. The first two are
computed from the declaration's *type*, with no dictionary involved; the
third is the older name-based hash and survives only for compatibility.

[cols="20%,40%,40%",options="header",]
|===
|Field |Computed from |Joins
|`+cross_prover_identity_key+` |SHA-256 of the canonical type shape: variable names renamed `+v0, v1, …+`, module paths dropped, operator spellings and binder keywords normalised, sorts canonicalised |Statements of the *same theorem* across provers that keep their binders and agree on sorts
|`+cross_prover_skeleton_key+` |The same shape with the binder prefix and sort atoms erased |Provers that elide binders (Isabelle writes `+"(x::nat) + y = y + x"+`) or use a different numeric sort (Why3: `+int+`)
|`+cross_prover_id+` |SHA-256 of the qualified name's _local tail_ |Only declarations whose local names happen to agree — kept for existing octad files and query clients
|===

`+identity_scheme+` records which rules produced the key (`+dk-shape-v1+`),
so a change of normalisation rules can never masquerade as a change of
theorem, and `+canonical_type+` keeps the rendered shape itself for
eyeballing and debugging.

The canonicalisation is purely syntactic: it does not know that `+x + y+
equals `+y + x+`, and deliberately does not try to. See
`+src/rust/corpus/canonical.rs+` and
`+docs/decisions/2026-10-22-structural-cross-prover-identity.adoc+`.

[source,text]
----
Agda     +-comm : ∀ (x y : ℕ) → x + y ≡ y + x
Coq      Lemma add_comm : forall x y : nat, x + y = y + x.
Lean 4   theorem Nat.add_comm (x y : Nat) : x + y = y + x := by omega
Idris2   addComm : (x, y : Nat) -> x + y = y + x
SMT-LIB  (assert (forall ((x Nat) (y Nat)) (= (+ x y) (+ y x))))
Dedukti  def add_comm : Π (x y : Nat), eq Nat (add x y) (add y x).
         ⟹ (PI [NAT NAT] (EQ (ADD v0 v1) (ADD v1 v0)))
----

Isabelle writes the same fact without binders and Why3 states it over
`+int+`; both land on
`+(EQ (ADD v0 v1) (ADD v1 v0))+` — the skeleton key — instead. Matching is
therefore *tiered*: exact structural key first, skeleton key second. Any
consumer that only compares one field should compare both.

A key is only as good as the parse behind it. `+StructuralKey::complete+`
says whether the canonicaliser read the *whole* statement; when it did not
(its parser stopped early, it met notation it has no rule for — HOL's `+!+`
and `+?+` binders, Isabelle's `+\<…>+` escapes — or a header drop discarded
the statement's own leading tokens), the key is still reported at the
structural tier but is a *prefix* that other statements share. Treat an
incomplete key as no identity at all. Measured on `+training_data/+`, the
share of statements read completely ranges from under 1% (Isabelle/ZF) to
over 90% (λProlog); see
`+docs/decisions/2026-10-19-lexicon-v2-and-identity-arbitration.adoc+`
(PR 3 results) and `+echidna lexicon scan+`.

The CLI surfaces it directly:

[source,bash]
----
$ echidna corpus identity add_comm --skeleton
<sha256-prefix>  [structural] 6 declaration(s) across 6 adapter(s)
  type: (PI [NAT NAT] (EQ (ADD v0 v1) (ADD v1 v0)))
  skeleton: (EQ (ADD v0 v1) (ADD v1 v0))
    agda     Ordinal.Brouwer.+-comm
    coq      Nat.add_comm
    dedukti  arith.add_comm
    idris2   Nat.addComm
    lean4    Nat.add_comm
    smtlib   bvadd_comm
----

=== Synonym table cross-prover joins

Each `+data/synonyms/<prover>.toml+` entry can carry a
`+semantic_class+` field. Entries with matching class — across any
prover — are considered equivalent under the same name:

[source,bash]
----
$ echidna corpus crossquery well-foundedness
Agda:   WellFounded
Coq:    well_founded
Lean:   WellFounded
Idris2: WellFounded
4 entries across 4 prover(s) for semantic class 'well-foundedness'
----

Use cases:

* *`+suggest+`* can fall back to a peer-prover’s name if the local one
isn’t found.
* *SA energy* can answer "`is `+osuc-mono+` proved in _any_ prover?`" in
one query.
* *Cross-prover proof exchange* (OpenTheory, Dedukti) consumes these
classes when translating goals.

Currently seeded: `+well-foundedness+`, `+accessibility+`,
`+wf-induction+`, `+wf-subrelation-transport+`. More entries land
alongside the proof work that needs them.

=== Limitations / known gaps

* *Adapter parsers are heuristic, not full grammars.* Coq’s notation
system, Lean 4’s macros, Idris 2’s mixfix all have edge cases the
line/keyword approach misses. Verified against real fixtures; iterate as
gaps surface.
* *Dependency edges store short names.* Cross-module name collisions
widen reverse-closures (over-conservative, which is the safer side for
impact analysis). Step 3’s `+cross_prover_id+` and octad provenance can
underwrite a follow-up content-addressed dep resolver.
* *The structural embedder is a baseline, not a model.* It hashes
1–3-grams of the canonical atom stream into 256 buckets, so it captures
type structure but not proof structure, and unrelated declarations that
share a type shape (e.g. two `+x = x+` lemmas) are near-identical by
construction. Swap in a GNN backend (`+Embedder+` trait) when the Julia ML
pipeline is primed against real corpora; the 256-dim structural vectors
are the baseline those runs are measured against.
