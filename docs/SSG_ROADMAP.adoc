= SSG Integration Roadmap
:toc:

== Status and evidence

The three SSG integration tracks below are retained design proposals.
The 2026-11-04 source review at `977ce94d9a83b8a3a47f54a67a14d004380fcdfa`
did not find the dedicated SSG renderer, MCP property-oracle service,
SSG-specific proofs, or extracted SSG library previously described here as
complete or in progress. Those implementation claims and the elapsed
2025 delivery dates are withdrawn. This document does not establish that
any SSG property has been proved or that an SSG integration is deployed.

The reusable ECHIDNA components that do exist are:

[cols="1,2",options="header"]
|===
|Component |Current source
|Prover backend interface |link:../src/rust/provers/mod.rs[ProverBackend]
|Agda backend |link:../src/rust/provers/agda.rs[Agda adapter]
|Z3 backend |link:../src/rust/provers/z3.rs[Z3 adapter]
|CVC5 backend |link:../src/rust/provers/cvc5.rs[CVC5 adapter]
|Aspect representation |link:../src/rust/aspect.rs[Aspect model]
|===

Their presence is a starting point for integration. It does not supply the
missing SSG implementation or qualify an arbitrary property encoding.

== Retained design tracks

=== Track 1: `echidna-docs` — proof content generation

*Status*: proposed; no dedicated implementation is qualified by this review.

The intended generator would render proof-bearing documents and expose
cross-prover references, aspect navigation, and dependency graphs.
Reusable backend parsing is available; the following work still needs an
implementation and tests:

* an HTML renderer that escapes content and preserves semantic structure;
* stable links between theorem identifiers and generated pages;
* a dependency graph derived from parsed proofs;
* a CLI with explicit error handling for unparsed or unsupported content;
* a supported-prover matrix established by actual fixtures and executions.

Do not infer support for a prover solely from its presence in ECHIDNA's
enum or from a successful executable version probe.

=== Track 2: `echidna-verify` — property oracle

*Status*: proposed architecture; no dedicated SSG MCP service is qualified.

The intended MCP tools are `verify_ssg_property`,
`compare_implementations`, and `generate_counterexample`.
Existing solver adapters can be reused, but each tool needs a specified
input language, property encoder, result contract, and tests.

A successful solver invocation alone is insufficient. The service must
record the exact input and encoding, selected backend and version,
timeout or unsupported result, and the evidence needed to interpret the
solver's answer. Cross-language comparisons require a shared semantics;
agreement between implementations does not establish that semantics.
Counterexample minimisation and fuzzing remain implementation work.

=== Track 3: `libechidna-ssg` — verified core library

*Status*: proposed specification and extraction work; no extracted library
or SSG-specific proof corpus is qualified.

The retained candidate properties are:

[cols="1,2",options="header"]
|===
|Property |Required clarification before proving it
|Rendering idempotence
|Define whether the output is also a valid input and which normal form is compared.
|Structure preservation
|Specify the source AST, output structure and the nodes that must be preserved.
|HTML well-formedness
|Choose the accepted HTML model and validation boundary.
|Template safety
|Specify escaping, trusted markup, URL handling and execution contexts.
|Determinism
|Bind configuration, dependencies, environment inputs and output ordering.
|===

A future Agda or Lean development must distinguish checked theorems,
explicit assumptions, incomplete proofs, and bounded test witnesses.
Extraction also needs an ABI and tests of the generated artifact; a source
proof does not automatically establish the behavior of an FFI consumer.

== Delivery gates

The previous 2025 dates were proposals and are not current completion
receipts. No replacement dates are asserted here.

. Specify one small end-to-end use case and its observable acceptance criteria.
. Implement the renderer or property encoder using the existing backend interface.
. Add positive and adversarial fixtures, including unavailable tools and unsupported inputs.
. Run the selected real backend and retain its command, version, input and result.
. Add proof obligations with explicit assumptions and rejection controls.
. Qualify extraction and bindings before describing a shared library as available.

Each gate needs evidence from the revision being assessed. A missing tool,
skipped test, unimplemented path or absent artifact remains unknown.

== Integration context and references

The proposed consumer is the polyglot SSG ecosystem. The role envisaged
for ECHIDNA is property checking and proof-content processing; that is an
integration goal, not a current service contract.

Earlier versions of this roadmap remain available in version control at
the source revision named above; they are historical proposals.
