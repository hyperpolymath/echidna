= ECHIDNA vocabulary recon — is the verification lexicon a priority?
:toc: macro
:toclevels: 2

*Date*: 2026-10-22
*Scope*: `data/synonyms/`, the corpus adapters that feed it (ProofNet,
MiniF2F), and the verification stack it is supposed to describe.
*Status*: recon complete; the first tranche of the fix is implemented in
this branch (see <<_what_changed>>).

== Verdict

*Yes — but for a different reason than "the corpora are the priority".*

The diagnosis in the brief is correct and measurable: the three shipped
maths dictionaries are undergraduate/competition pure mathematics, and
essentially none of the vocabulary this repository's own verification
surface is written in exists in them. I re-ran the check and got 21 of 23
probe concepts in the brief with **zero** occurrences anywhere under
`data/synonyms/` (the two hits were incidental substrings, not entries).

The reason this is a priority is *not* that ProofNet or MiniF2F are
wrong. They are correct for what they are: ProofNet is textbook
undergraduate problems (Rudin, Munkres, Dummit-Foote) and MiniF2F is
olympiad problems. Both adapters in `src/rust/corpus/` say so in their
module docs. They should stay exactly as they are.

The priority comes from Stage 1d of `docs/ROADMAP.adoc`: *"vocab covers
the surface [255 K; target ~1 M]"*. The repository's surface includes
`src/abi/` (Idris2), `ffi/zig/` (Zig), `spark/`, `crates/echidna-core-creusot/`,
and the Julia/Chapel layers. That surface has no semantic classes at all
today, so the cross-prover join cannot carry it. That gap is real,
load-bearing, and orthogonal to the maths corpora.

=== One honest caveat about priority

The dictionaries are *loaded* on every run but almost nothing *consumes*
them yet:

[cols="1,1,3"]
|===
| Dictionary | Loaded by | Read by a consumer?

| `_msc2020.toml`
| `load_cross_prover_dicts` (Rust); `load_msc2020` (Julia)
| Partly — `src/julia/run_training.jl:116` pre-loads it at training launch
  so TOML breakage surfaces early. Its own comment says "currently consumed
  downstream; data path only".

| `_wordnet_math.toml`, `_conceptnet_seed.toml`, `_disciplines.toml`,
  `_verification_systems.toml`
| same loader
| No. In Rust, `load_cross_prover_dicts` is called only from
  `tests/lexicon_v2_test.rs`. There is no ranking path that reads
  `by_semantic_class` yet.
|===

So the correct framing is: *the vocabulary is a latent asset*. Expanding
it is cheap and safe now, and it unblocks Stage 1d/2b; but nobody should
expect a metric movement until a consumer joins on `semantic_class`. I
have not pretended otherwise in the commit or the CHANGELOG.

== What the repository actually is

ECHIDNA is a neurosymbolic theorem-proving platform: a Rust core
orchestrating ~128 `ProverKind` backends through a trust-hardening
pipeline (integrity hashing, axiom tracking, certificate checking,
5-level confidence), with 20 corpus adapters, six exchange formats, four
arbitration mechanisms, a Julia ML side, a Chapel parallel layer, an
Idris2 ABI and a Zig FFI. The synonym layer is one small part of it — it
feeds `echidna suggest` (the variant tester) and cross-corpus
`semantic_class` resolution.

== Corrections to the brief (before they cost you work)

1. *"~250 codes across 68Qxx / 68Nxx / 03B70" is arithmetically
   impossible.* MSC2020 defines **26** codes in 68Qxx, **10** in 68Nxx,
   and exactly **one** 03B70. Hitting 250 in those sections would mean
   inventing codes. I delivered the honest ceiling instead: *all* of
   68Qxx and 68Nxx, the whole of 03B (28 codes) plus the 03C/03D/03F
   codes that bear on verification, the 68M/68P/68T/68V/68W ring and
   06B35 — 181 codes total, every one checked against the zbMATH MSC2020
   listing.
2. *The existing `_msc2020.toml` was not just sparse, it was wrong in
   places.* Fifteen rows carried MSC2010 or transferred wording:
   * `03B15` and `68T15` are MSC2010-only codes; MSC2020 splits
     `03B15` into `03B16` (higher-order logic) + `03B38` (type theory)
     and renumbers `68T15` as `68V15`.
   * All four `68V` rows were wrong: `68V05` is *proofs-by-exhaustion*
     (not "computer-aided proof"), `68V25` is *math markup* (not
     "proof assistant"), `68V30` is *MKM* (not "proof certificate"),
     `68V35` is *digital math libraries* (not "MKM").
   * `03D03` said "computability / Turing machine" but is *Thue and Post
     systems*; `03F50` said "PA / PRA" but is *metamathematics of
     constructive systems* (PA is 03F30).
   * `06A11` said `well_founded`; it is *chain conditions*, a different
     property. `18N10` listed monoidal categories; it is *2-/bicategories*
     (monoidal is 18M05).

   These are repaired in place with a note naming the MSC2020 code, and
   the two MSC2010-only rows are kept deliberately so pre-2020 metadata
   still resolves.
3. *Row-count targets now in the tree*: `_wordnet_math` is 81 rows (not
   "~80"), `_conceptnet_seed` is 53 (not "~55"). Docs in `README.adoc`,
   `EXPLAINME.adoc`, `docs/CORPUS-ADAPTERS.adoc` and
   `data/synonyms/README.adoc` now carry the real numbers.
4. *"A fourth dictionary"* — the tree already had four cross-prover
   dictionaries (`_msc2020`, `_wordnet_math`, `_conceptnet_seed`,
   `_disciplines`), and the docs said "three" because `_disciplines` was
   added later and never folded into the prose. The new file is the
   fifth, and `CrossProverDicts` now exposes it as
   `verification_systems`.

== Estate policy

The brief's clarification is recorded in `data/synonyms/README.adoc` and
reflected in the dictionary's estate section:

* *ABIs in Idris2* — `idris2_abi`, `abi_contract`, `abi_representation`,
  `abi_stability_guarantee`, `totality_proof`, `foreign_descriptor`,
  `opaque_handle`, `handle_lifetime`.
* *APIs and FFIs in Zig* — `zig_api`, `zig_ffi`, `exported_symbol`,
  `symbol_table`, `marshalling`, `boundary_ownership`, `out_parameter`,
  `error_code`, `null_at_boundary`, `string_at_boundary`,
  `callback_into_host`.
* *SNIFs, not bare NIFs* — `snif`, `snif_contract`, `nif`, `dirty_nif`,
  `nif_resource`, `term_lifetime`, `scheduler_thread`,
  `blocking_call_discipline`, `beam_process`,
  `resource_release_callback`, `panic_across_boundary`,
  `result_into_beam`. The repo had **no** SNIF vocabulary at all before
  this change.
* *Rust/Creusot* — `rust_creusot_layer`, `creusot_annotation`,
  `creusot`, `why3`; the vocabulary describes annotated Rust, not
  "Rust plus hope".
* *Julia and Chapel for their layers* — `julia_layer`, `chapel_layer`,
  `ipc_channel`, `sidecar`, `polyglot_boundary`, `language_ownership`.
* *No Python* — `no_python_dependency`, and `git ls-files '*.py'` returns
  zero files. This recon used Python only as throwaway tooling in `/tmp`
  (a TOML generator and a Nickel-contract mirror); nothing Python is
  added to the tree.

== Validation performed

* *Contract*: `cargo` is absent from this sandbox, and the pinned Nickel
  release binary is unreachable (its GitHub release asset redirects to
  `release-assets.githubusercontent.com`, which is outside the allowed
  egress set), so `scripts/lexicon-check.sh` and `cargo test` could not
  run here. I mirrored `schema.ncl` rule-for-rule in a throwaway checker
  and ran it over all 19 tables plus the 18 fixtures: **19 tables, 1381
  rows, 0 failures**, and all 17 reject fixtures still reject. The
  mirror's only divergence is deliberate: it treats empty `aliases` and
  self-aliases as warnings rather than errors, because `schema.ncl`
  permits both (`mizar.toml` relies on empty alias lists).
* *CI must still run the real gate*: `just lexicon-check` (Nickel +
  `tests/lexicon_v2_test.rs`). `tests/lexicon_v2_test.rs` now also
  asserts the new dictionary is non-empty, that its classes resolve, and
  that `merge_cross_prover_dicts` reaches them, so a silently-empty file
  fails rather than passing as "loads fine".
* *No Python in tree*: `git ls-files '*.py'` → 0.
* *No deletions*: no existing row removed; 19 rows corrected, each with a
  note explaining the MSC2020 wording.
