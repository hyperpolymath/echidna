= Re-recon: routing surfaces and the rule-engine source

*Status*: current. Supersedes nothing; this is the first pass that classifies
*every* client-facing path in the tree rather than only the ones a given
consumer happens to use. *Date*: 2026-11-01. *Method*: static read of the
checkout at `916b769` — no build, see <<limits>>.

This document answers four questions that were being asked of different
documents with different answers:

. Is the VeriSimDB bridge a *persistence adapter* or a *mandatory VCL
communication path*?
. How does that reconcile with clients that call the echidnabot REST/GraphQL
surfaces directly, and with proof-burrower's `echidna prove` subprocess
contract?
. Which rule engine is live — the Logtalk module in `rules/`, or the Elixir
rules in Hypatia?
. Which paths in the tree are *active*, *compatibility-only*, *archival* or
*dead*?

== 0. Verdicts

*VeriSimDB is a persistence adapter, not a bus.* It is behind the non-default
`verisim` Cargo feature, it is written to fire-and-forget, and no prover is
reached through it. Nothing in the default build contacts it. There is exactly
one exception, and it is an accident rather than a design: enabling `verisim`
also switches `POST /api/prove` from "factory + backend" onto
`ProverDispatcher` (<<rd1,RD1>>). Persistence should not be the switch that turns
the trust pipeline on.

*VCL-UT is a query layer over VeriSim octads, not a transport ECHIDNA requires.*
In a default build `vcl_ut::cross_prover_search_names` is a stub returning
`Ok(vec![])` and `QueryExecutor` holds a `PhantomData`. A client that never
enables the feature never pays for it.

*Clients do not need any of that.* echidnabot talks to `/api/*` (core server)
or `POST /` (the separate `echidna-graphql` binary); proof-burrower looks for
`echidna prove --output json` and reads one JCS line off stdout. Those three
paths are independent and none of them routes through VeriSimDB.

*The Logtalk material is dead and has been quarantined.* `rules/security_learning.lgt`
was the only `.lgt` file in the tree, referenced by nothing — not a test, not a
workflow, not a Justfile recipe, not the REUSE manifest's per-file headers.
Estate rule authoring is Elixir in Hypatia. The file now lives under
`archive/logtalk/` with a status header; `rules/` no longer exists.

*Two routing defects were fixed en route* (container entrypoint and health
probes, <<rd3,RD3>>), *one was documented and left open* (the 8081 port collision,
<<rd2,RD2>>), *and one is a live correctness gap* (integrity checking never
configured, <<rd5,RD5>>).

*Follow-up (2026-11-04):* RD2 is now repaired: the GraphQL default is 8082,
while the core server remains on 8081. The release note describes the client
migration and the explicit override for deployments retaining the old address.
The original 2026-11-01 observation is retained below as history.

== 2. VeriSim: adapter, not a communication path

=== 2.1 What the feature flag actually gates

`+verisim+` is off in `+default = []+` (`+Cargo.toml:118+`). It enables
`+dep:ciborium+` (the CBOR encoder for the Semantic octad) and four call sites:

[width="100%",cols="34%,22%,44%",options="header"]
|===
|Call site |Direction |Behaviour when absent

|`+dispatch.rs:725+` `+spawn_record_attempt+`
|write
|`+tokio::spawn+`ed `+record_proof_attempt+` after each dispatch exit. Errors
logged at `+warn+` and swallowed. *Cannot* fail a dispatch.

|`+dispatch.rs:207+` `+VeriSimAdvisor+`
|read
|`+verify_proof_verisim_guided+` asks
`+mv_prover_success_by_class+` which prover to try. Any error → caller's
fallback prover. Advisory only.

|`+vcl_ut.rs:349+` `+QueryExecutor+`
|read
|`+PhantomData+` stub; `+cross_prover_search_names+` returns `+Ok(vec![])+`
(`+vcl_ut.rs:951+`).

|`+server.rs:104+`
|wiring
|`+with_verisim_writer(VERISIM_URL)+`; absent → dispatcher with no writer.
|===

Read that table as a whole: every one of the four is a *side effect on, or a
hint to*, a proof run. None of them carries a proof request, a proof result, or
a client command.

=== 2.2 The one place the flag changes routing

`+POST /api/prove+` is compiled twice (`+server.rs:423–445+`):

* with `+verisim+`: `+app_state.dispatcher.verify_proof(...)+` — trust pipeline;
* without: `+ProverFactory::create+` then `+parse_string+` directly — no
  dispatcher.

So the presence of a *storage* feature decides whether this HTTP proof enters
the dispatcher. This single-prover call does not produce an arbitration
verdict. Two consequences worth stating plainly:

. A deployment that wants the trust pipeline must enable a database
  integration it may not have, and point it at a URL that will then be probed.
. A deployment that enables it for the learning loop silently changes its
  verification routing.

This is recorded as <<rd1,RD1>>. It is not fixed here: the fix is a behaviour
change that deserves its own decision record, and any consumer that currently
relies on the flag to select the pipeline would be moved by surprise.

=== 2.3 What never touches VeriSim

`+echidna prove+` (human and `+--output json+`), `+/api/verify+`,
`+/api/verify_raw+`, `+echidna-rest+`, `+echidna-graphql+`, `+echidna-grpc+`,
`+echidna-mcp+`. `/api/search` and `+echidna search+` *do* consult VCL-UT, but
only to append cross-prover results, and only in a `+verisim+` build — the
stub swallows the call otherwise (`+server.rs:1043+`, `+main.rs:924+`).

=== 2.4 Drift found in the VeriSim surface

* `+.machine_readable/integrations/verisim.a2ml+` declares `+format = "hexad"+`
  and a `+verisimdb-data/feeds/+` destination. The implemented and formally
  specified model is an *octad* (8 modalities,
  link:../architecture/VERISIM-ER-SCHEMA.adoc[`+VERISIM-ER-SCHEMA.adoc+`]).
  "Hexad" is not a modality count that exists anywhere in the tree.
* link:../design/ECHIDNA-VERISIM-TRIANGULATION-2026-04-17.adoc[`+ECHIDNA-VERISIM-TRIANGULATION-2026-04-17.adoc+`]
  describes the *workflow* for absorbing provers and predates the entity model.
  `+VERISIM-ER-SCHEMA.adoc+` says it "replaces the aspirational text" there.
  Classified archival below; not edited.
* `+docs/ECOSYSTEM-INTEGRATION.adoc+` still lists VeriSimDB as "🔄 Manual" with
  a `+ingest-scan.sh+` recipe. The *code* path (octad writer + `proof_attempts`
  table) is more advanced than that recipe; the recipe is a separate,
  scanner-driven ingestion route that predates it. Both are real; neither is
  the other.
* `doc/…`-level claim "HTTP push deferred" in
  `+.machine_readable/descriptiles/ECOSYSTEM.a2ml:29+` is correct for the
  corpus adapter and incorrect for `+dispatch.rs+`, which pushes today. The two
  paths emit different payloads (octads vs corpus records) and both are live.

== 3. Client reconciliation

=== 3.1 echidnabot, calling REST or GraphQL directly

Two independent surfaces, and the doc has to name which:

* *Core server* (`+/api/prove+`, `+/api/verify+`, `+/api/provers+`,
  `+/api/health+`) — port 8081 by default, route table in
  `+src/rust/server.rs+`. This is what published examples and
  `+server-boot-gate.yml+` exercise.
* *`+echidna-rest+`* (`+/api/v1/proofs+`, `+/api/v1/provers+`, …) — port 8000,
  OpenAPI + ReDoc. Different paths, different session store, no `/api/prove`.
* *`+echidna-graphql+`* — `+POST /+` on 8082 (8081 before 2026-11-04). Queries are `+provers+`,
  `+proofState(id:)+`, `+listProofs+`, `+suggestTacticsByProofId+`,
  `+proverStatus+`, `+health+`; mutations `+submitProof+`, `+applyTactic+`,
  `+cancelProof+`, `+verifyProof+`, `+suggestTactics+`.

A GraphQL client using the former 8081 default must move to 8082, or deliberately
configure `ECHIDNA_GRAPHQL_ADDR` to a free address. The core server remains on
8081. See <<rd2,RD2>> and the 2026-11-04 changelog migration entry.

*Trust honesty for core HTTP clients*: `/api/verify` never enters the dispatcher
(`+server.rs:519+`), and `/api/verify_raw` execs the solver binary directly by
design. `/api/prove` enters the dispatcher only in a `+verisim+` build, as a
single-prover call without arbitration. `/api/verify_parallel` enters the
dispatcher independently of that feature. A client cannot identify the trust
path from the two single-prover response shapes:
`+ProveResponse+` is `+{success, goals, message}+` and `+VerifyResponse+` is
`+{valid, outcome, goals_remaining, tactics_used, mode, smt_status}+`. Neither
carries a schema identifier or a trust level, unlike the prove contract. That
asymmetry is the strongest argument for pointing new clients at
`+echidna prove --output json+` rather than HTTP.

=== 3.2 proof-burrower, the `+echidna prove+` subprocess contract

This is the best-specified client path in the tree and it needs no network at
all:

* one line, JCS-canonical, on stdout; logs and `+--diagnose+` on stderr;
* `+status+` ∈ `+verified | failed | error | timeout | unknown+`, derived from
  `+ProverOutcome+` via a total mapping;
* `+trust.confidence+` is `+null+` on this path *always* — a single-backend
  check verifies no certificate, so there is no receipt. This is the
  receipt/warrant distinction applied honestly, and it matches where
  `+epistemic-types+` has landed: ECHIDNA copies the distinction as a pattern,
  it does not depend on the Agda library and does not claim interop with it;
* exit code 0 iff `+verified+`;
* capability detection by probing `+echidna prove --help+` for `+--output+`.

Feature-detection matters: the contract is *additive* per its own versioning
rules, so older binaries answering without `+--output+` are still usable, and
new clients must ignore unknown fields.

=== 3.3 `+echidna-mcp+` — the client that drifted

`+crates/echidna-mcp/src/main.rs+` invokes:

* `+echidna prove <file> --format json+`. `+--format+` *is* a global flag
  (`+main.rs:43+`, `+global = true+`) so this parses, but it selects the CLI
  formatter (`+{"level":"success",…}+`), not the prove contract. The tool then
  sniffs for `+"level": "success"+`. It works and it is the *legacy* shape: a
  second, undocumented JSON dialect for the same operation.
* `+echidna list-provers --format json+` — parses; no contract at all.
* `+echidna check-prover <name>+` — *no such subcommand exists*
  (`+Commands+` in `+main.rs:57–450+` has no `+CheckProver+`). The tool fails
  with a clap usage error every time.

Recorded as <<rd4,RD4>>. Not fixed here: the correct repair is a rewrite onto
`+--output json+` plus a `+check-prover+` subcommand or a `/api/provers` probe,
which is a feature decision, not a rename.

=== 3.4 What no client can get today

* A partial-progress field. The contract has no "remaining subgoals"; a swarm
  that wants to score partial attempts must parse prover output.
* A receipt-backed confidence via HTTP. `+/api/prove+` has no `+trust+` object.
* A single surface that is both OpenAPI-described and trust-pipeline-backed.

None of these are bugs in the contract. They are the current *scope*, and the
useful thing a recon can do is stop other documents implying otherwise.

== 4. Logtalk: what was left and why it is dead

=== 4.1 What was there

`+rules/security_learning.lgt+` — 234 lines, two Logtalk objects
(`+security_learning+`, `+cicd_integration+`), dated 2025-12-29. It encodes 20
alert categories from cicd-hyper-a's `+ERROR-CATALOG.scm+`, a severity
classifier, a fix-suggestion table, seven prevention workflows, and a
`+assertz+`-based "learning" loop that re-derives rules from its own training
data.

=== 4.2 Why it is dead

* *Nothing loads it.* `+grep -rn '\.lgt' --exclude-dir=.git .+` returns the file
  and one self-reference inside it. No test, workflow, Justfile recipe, A2ML
  manifest or Cargo build step names it. No `+logtalk+`/`+swipl+` binary is
  referenced anywhere in CI.
* *Its inputs are on someone's disk.* `+cicd_repo_path('~/repos/cicd-hyper-a/.audittraining')+`
  — a home-directory path with a literal `+~+`, in an object whose job is to
  open it. Not portable, not parameterised, not a contract.
* *Its learning loop cannot learn.* `+load_training_data/1+` calls
  `+read(Stream, Term)+` on a Prolog stream but the file it is pointed at is a
  Scheme source (`+ERROR-CATALOG.scm+`). Every term fails
  `+process_training_term/1+` and hits the catch-all `+process_training_term(_)+`.
  `+learn_rules/0+` then asserts whatever the static tables already said. The
  output is a transcript of the input constants.
* *The estate moved.* `+docs/ECOSYSTEM-INTEGRATION.adoc:117+` described Hypatia
  as auto-generating Logtalk rules after 5+ observations. Hypatia's rule
  engine is Elixir; the estate's rule-as-data path is Elixir rule modules, not
  Logtalk objects. An ECHIDNA-side Logtalk module was never a consumer of that
  output, even when the prose was accurate.
* *The one live rule surface in this repo is `+.hypatia-baseline.json+` +
  `+.hypatia-ignore+`* — i.e. ECHIDNA is a Hypatia *target*, not a rule
  producer.

== 5. Path classification

Four classes, used strictly:

* *active* — built, called, or deployed by something in this tree today;
* *compatibility-only* — works, but exists to serve a consumer or a shape that
  a newer path supersedes; must not gain new capability;
* *archival* — retained as a record; explicitly not a build or usage
  instruction;
* *dead* — nothing loads it and nothing can.

[[rd1]]
=== RD1. `+verisim+` is a routing switch as well as a storage switch
*P1 — structural, open.*

`+server.rs:423+` compiles `/api/prove` two ways; whether an HTTP proof enters
`+ProverDispatcher+` depends on a database feature. No caller-visible field
distinguishes the two behaviours.

*Fix direction* (not applied): build the dispatcher unconditionally and make
`+with_verisim_writer+` purely additive — the writer already cannot fail a
dispatch, so nothing needs the compile-time branch. Requires a decision record
because it changes what a default build returns.

*Reproduce:*
[source,bash]
----

grep -n 'cfg(feature = "verisim")' src/rust/server.rs

[[rd2]]
=== RD2. Core server and GraphQL interface originally shared default 8081
*P1 — fixed 2026-11-04; original observation retained.*

`+main.rs:165+` (`+server --port+` default 8081) and
`+src/interfaces/graphql/main.rs:39+` (`+127.0.0.1:8081+`, hard-coded). Whichever
starts second cannot bind. `+docs/QUICKSTART-USER.adoc+` claimed the three
interfaces sit "on dedicated ports (8081 / 50051 / 8000)" — false for the first
two pairings.

This is a policy matter, not a preference:
`+0-canon/PORT-REGISTRY.adoc+` in hyperpolymath/standards says "`Every project
MUST use a unique port. No two projects share a port.`" The registry is
prose-only today ("`no gate reads this registry`"), which is why the collision
survived a release.

Done here: `+ECHIDNA_GRAPHQL_ADDR+` override (default unchanged, so no client
breaks), and explicit collision warnings in `+site/docs/index.adoc+`,
`+site/docs/api/graphql.adoc+` and `+QUICKSTART-USER.adoc+`, plus
`+core-server = 8081+` in the `+[interfaces]+` block of `+META.a2ml+` so the
machine record cannot omit it.

Follow-up on 2026-11-04: the GraphQL default moved to 8082, with a release
note and current interface documentation updated together. Clients using
the old GraphQL default must update their endpoint, or deliberately set
`+ECHIDNA_GRAPHQL_ADDR=127.0.0.1:8081+` while keeping the core listener off
that address. Invalid and occupied overrides now return contextual startup
errors.

*Reproduce:*
[source,bash]
----
grep -n 'default_value = "8081"' src/rust/main.rs
grep -n -A 1 'VarError::NotPresent' src/interfaces/graphql/main.rs
----

[[rd3]]
=== RD3. Container entrypoint and health probes targeted strings that do not exist
*P2 — fixed.*

`+entrypoint.sh+` ran `+echidna serve+` (subcommand is `+server+`, no alias);
`+compose.toml+` probed `+/health+` and `+vordr.toml+` probed `+/ready+`, neither
of which the core server serves. Net effect: the published container could not
start, and would have been unhealthy if it had.

Three-line fix in each file; `+/api/health+` is the real route
(`+server.rs:173+`).

*Adjacent, found and deliberately not fixed.* `+container/compose.toml+` is not
valid TOML 1.0: its `+environment = { … }+` inline tables span multiple lines,
which TOML forbids. `+selur-compose+` accepts the dialect, but the file's own
header offers `+podman compose --file compose.toml+` as the fallback when selur
is absent, and a strict parser rejects the file before it looks at the routes
(verified: Python's `+tomllib+` fails at line 19, column 16, on both the
pre-and-post-change file). Rewriting the tables to `+[services.echidna.environment]+`
would fix the fallback but changes what selur reads, so it needs whoever owns
the selur format to confirm rather than a guess.

[[rd5]]
=== RD5. Solver integrity checking is never configured
*P1 — open, and the largest gap this pass found.*

`+docs/ARCHITECTURE.adoc+` promises step 1 of the trust pipeline is
`+integrity/+`: "solver binary SHAKE3-512 + BLAKE3 against
`+config/solver-manifest.toml+`". In `+dispatch.rs:632–645+` the check runs only
`+if let Some(ref checker) = self.integrity_checker+`, else
`+solver_integrity_ok = true+`. `+with_integrity_checker+` has *no caller
anywhere in the tree* (`+grep -rn with_integrity_checker src/ crates/ tests/+`
returns the definition only). And `+config/solver-manifest.toml+` still carries
`+shake3_512 = "PLACEHOLDER_COMPUTE_ON_FIRST_RUN"+` for every solver, so
configuring a checker today would report `+Uninitialized+` — which the code
treats as passing.

So: integrity is *assumed* ok on every path, and the manifest could not prove
otherwise if it were consulted. Report as a gap; wiring it is a decision (it
introduces a failure mode where a proof is refused for a hash mismatch).

*Reproduce:*
[source,bash]
----

grep -n 'PLACEHOLDER' config/solver-manifest.toml
----

[[limits]]
== 7. Limits of this pass

No build was run and none could be: this checkout has no cargo toolchain, no
`+agda+`, no Creusot, and no network access to a crate registry. Everything
above is a static read of source and configuration at `916b769`. Where a claim
depends on runtime behaviour it says so and gives the command that would settle
it.

By the ledger vocabulary of `+PROOF-POLICY.adoc+` §5, that makes the *whole
document* `+argued+` — a transcription no kernel, compiler or test runner
checked. The claim ledger in §0.1 grades the individual claims; none of them is
above `+proven+`, and the ones that reach `+proven+` (by construction) only do
so for facts decidable by reading, such as "no `+serve+` variant exists" or
"this branch is `+cfg`-gated". By the Mathesis grades this is at best *Grade 3*
in shape — locally consistent, untranslated, independently unchecked — and the
Agda legs are *not* even locally checked here, since no Agda is installed.

Claims about other repositories — proof-burrower's parser tolerance,
echidnabot's client wiring, Hypatia's generated-rule format — are taken from
this repository's own records and are *not* independently verified here. The
`+issues/+` drafts already mark such claims *[unverified]*; this document keeps
that discipline.

Scope note: `+epistemic-types@5422cd5+` (22 strict-safe Agda modules, Kripke
semantics, receipt/warrant split) is *context* for what ECHIDNA may claim, not a
dependency. `+docs/PROVE-RESULT-CONTRACT.adoc+` and
`+crates/echidna-core/src/prove_result.rs+` both describe the relationship as
"copies the distinction as a pattern; does not depend on the Agda library" —
which is the accurate, scoped statement, and this recon found no place
overclaiming universal interoperability.

=== 10.1 The receipt that matters

[source,bash]
----
cd meta-checker
agda --safe --without-K --cubical-compatible src/Echidna/MetaChecker.agda
# exit 0, 98 s cold, 9 modules + 214 stdlib modules
----

Agda 2.7.0.1, `+agda-stdlib+` 2.1, commit `+916b769+`. Zero postulates — and now
excluded by `+--safe+` rather than by a `+grep+`, which is the difference between
`+argued+` and `+proven+` in §5 of the policy.

**The limit, stated as a limit.** 53 warnings, all
`+-W[no]UnsupportedIndexedMatch+`, at `+TrustLevel+` 77/88/235,
`+AxiomSafety+` 119 and `+ClampTrust+` 98. Those functions do not *compute*
under Cubical transports. The corpus is `+--cubical-compatible+`, **not**
`+--cubical+` — `+PROOF-POLICY+` §2.1 draws exactly that distinction, and it is
why the flag stays and the warning is reported instead of suppressed.

The obvious question — why not use `+--cubical+` and be done with it — was
tested rather than argued: `+agda --cubical --safe src/Echidna/MetaChecker.agda+`
fails **inside stdlib 2.1** (`+Data/List/Membership/Setoid/Properties.agda+`,
unsolved metas) before reaching any ECHIDNA module. The stdlib is written to be
`+--cubical-compatible+` and ships `+--warning=noUnsupportedIndexedMatch+` for
itself. So the flag chosen is the strongest the dependency set supports, and the
warning is a limit to record, not a weakness to hide.

One more result worth having: the out-of-policy `+proofs/agda/+` tree — the one
R6 cites — is **13/13 green** under the same flags. That does not make it
in-policy, but it does change R6's remedy from "downgrade the claim" to "move the
file".

=== 10.2 A module that had never been compiled

`+meta-checker/src/Echidna/AxiomTrackerCompleteness.agda+` was in the tree, and
in the "30+ properties" summary, but nothing imported it and no workflow named

existence was being reported as evidence. Two fixes and it is now in the
closure, and `+agda-meta-checker.yml+` gained a step that fails if any module
