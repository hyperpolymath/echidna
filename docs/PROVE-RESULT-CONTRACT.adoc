= The `echidna.prove.result/1` contract
:toc: macro

`echidna prove <file> --output json` prints the result of one prove run as
machine-readable JSON. proof-burrower and echidnabot consume it; any other
client may. Human output stays the default: without `--output json`,
`echidna prove` behaves exactly as before.

toc::[]

== Shape

Exactly one line on stdout, terminated by one newline. The line is a single
JCS-canonical (RFC 8785) I-JSON (RFC 7493) object:

[source,json]
----
{"duration_ms":1,"echidna_version":"<cargo version>","goal":"ok.twasm","message":"PROVED in 0ms","prover":"TypedWasm","schema":"echidna.prove.result/1","status":"verified","trust":{"axioms":[],"confidence":null}}
----

[cols="1,1,4",options="header"]
|===
| Field | Type | Meaning

| `schema` | string | Always `echidna.prove.result/1`.
| `status` | string | `verified`, `failed`, `error`, `timeout` or `unknown` (below).
| `prover` | string | The backend, as its `ProverKind` variant name (`Lean`, `Isabelle`, `TypedWasm`, ...). Empty when no backend could be selected.
| `goal` | string | The proof file path, exactly as given on the command line.
| `duration_ms` | integer | Wall-clock time of reading, parsing and checking, in milliseconds. Saturates at 2^53 − 1.
| `message` | string | Human-readable diagnostic. For a completed check it is the outcome (`PROVED in 12ms`, `NO_PROOF_FOUND in 40ms`, `TIMEOUT after 300s`, ...); for an `error` it is the error chain.
| `trust.confidence` | number or null | A receipt-backed confidence in [0, 1], or `null`. See <<receipt>>.
| `trust.axioms` | array of strings | Axioms and escape hatches (`sorry`, `Admitted`, `postulate`, ...) that ECHIDNA's axiom tracker found in the input, sorted and de-duplicated.
| `echidna_version` | string | The version of the `echidna` binary that printed the object.
|===

Logs go to stderr in this mode. With `--diagnose`, the failure diagnostic
for a run that was not `verified` also goes to stderr.

== Status mapping

Each backend check returns a `ProverOutcome`
(`src/rust/provers/outcome.rs`). `ProverOutcome::prove_status` maps it:

[cols="2,1,3",options="header"]
|===
| `ProverOutcome` | `status` | Why

| `Proved` | `verified` | The backend established the goal.
| `NoProofFound` | `failed` | The backend ran to completion without establishing it.
| `Timeout` | `timeout` | The configured budget ran out; retry with a larger `--timeout`.
| `InconsistentPremises` | `unknown` | Anything follows from inconsistent premises, so this is neither a usable proof nor a refutation.
| `InvalidInput`, `UnsupportedFeature`, `ProverError`, `SystemError` | `error` | The input, the backend or the system failed.
|===

Failures before the check (no backend for the file extension, unreadable
file, parse failure, backend construction failure) are also `error`
objects. stdout never carries anything but the one object.

== Exit code

`0` when `status` is `verified`, `1` otherwise. This matches the human mode,
which also exits 1 on a failed proof.

[[receipt]]
== Receipt, not warrant

`trust.confidence` is a number only when a receipt-backed computation
produced it, such as an independently checked proof certificate. The
`echidna prove` path checks a single backend and verifies no certificate,
so today it always reports `null`. It never reports a guessed or
model-derived score as confidence.

This follows the factive / non-factive distinction of
`hyperpolymath/epistemic-types` (`FactiveModality`): a receipt is
transported proof, a warrant is only evidence. ECHIDNA copies the
distinction as a pattern; it does not depend on the Agda library.

== Consuming it from Rust

The type, the serialiser and a strict parser live in `echidna-core`
(`echidna_core::prove_result`), so a client does not need to re-implement
them:

[source,rust]
----
use echidna_core::prove_result::{ProveResult, ProveStatus};

let result = ProveResult::parse(&stdout)?;   // rejects non-canonical input
if result.status == ProveStatus::Verified { /* ... */ }
----

See `crates/echidna-core/README.adoc` for the git-dependency recipe.

== Detecting support

Older binaries do not have the flag. A client can run `echidna prove --help`
and look for an `--output` token, as proof-burrower does.

== Versioning

Adding a field is compatible: consumers must ignore unknown fields.
Removing, renaming or retyping a field, or adding a status value, needs a
new schema identifier (`echidna.prove.result/2`).

== Status of this feature

* Implemented: `src/rust/prove_contract.rs`, `src/rust/main.rs`
  (`prove_json_command`), `crates/echidna-core/src/prove_result.rs`.
* Tested: golden JCS bytes for every status (`echidna-core` and
  `prove_contract` unit tests); planted non-canonical payloads are
  rejected; end-to-end runs of the real binary for `verified`, `failed`
  and `error` (`tests/prove_output_json.rs`). `timeout` and `unknown` are
  covered only by the golden unit tests, because no backend that runs
  without an external prover produces them.
