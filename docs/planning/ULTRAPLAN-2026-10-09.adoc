== Executive summary

=== The thesis

ECHIDNA's core promise is one sentence: *a result that leaves ECHIDNA has been
checked as far as its label says, and the label is honest.* The repository
already has the right _types_ for this promise. There is a rich prover outcome
enum (`ProverOutcome`, with `Proved`, `NoProofFound`, `InvalidInput`,
`UnsupportedFeature`, `Timeout`, `InconsistentPremises`, `ProverError`,
`SystemError`), a trust level hierarchy, a solver-integrity status, a sandbox
mode, and a certificate flag. The promise breaks at the _wiring_. Each of those
safeguards can be skipped silently:

* the CLI `verify` command branches on a boolean and throws away the typed
  outcome;
* the integrity checker has no production caller, its manifest holds only
  placeholder hashes, and `Uninitialized` counts as a pass;
* the `--sandbox` flag is parsed and never read, so `--sandbox podman` runs the
  solver unsandboxed;
* certificate generation is a config field that nothing reads;
* the SPARK theatre gate passes with contract enforcement switched off, and
  `gnatprove` runs in no workflow;
* the public API that accepts proof content is deliberately unauthenticated,
  runs solver subprocesses on request content, and auto-deploys whatever
  `:latest` points to.

None of this is hidden. It is written down in the README and in `CLAUDE.md` as
present-tense fact. The gap between claim and code is the single largest risk
to the project's long-term value, larger than any missing prover or missing
feature.

=== The diagnosis in one table

[cols="1,3"]
|===
| Symptom | Root cause (generator-level)

| Integrity and sandbox are advertised but skipped
| Safeguards are optional stages wired to defaults that turn them off, and the
  defaults are not recorded in the result. Config fields exist that nothing reads.

| The learning loop can be trained on environment failures
| The CLI collapses environment errors into "invalid". Stage 3 is defined as a
  model that "improves from outcomes" (ROADMAP). If a missing Coq library path is
  recorded as a failed proof, the training signal is about the environment, not
  the mathematics. (Inference; see section 3.4.)

| CI is green in the places that matter and red in the places that don't
| The required-check set on `main` omits the gates that fail most often
  (governance, workflow lint, Hypatia). Some checks can pass without running
  anything: conditional pass-throughs, skipped jobs, and allow-fail jobs. Allow-fail units have no expiry until the CI hygiene PR (#416) adds one.

| Status documents disagree with each other and with the tree
| Several hand-typed status documents are stale by months, and the in-repo
  rulesets do not match the live ones. No document is generated from the
  code or from CI.

| Community is single-maintainer
| 139 commits to `main` since 2026-07-01: 103 by the owner, 33 by dependabot,
  3 by the agent bot, and no external human contributor. Six stars, zero forks.
|===

=== The plan in ten moves

. *Contain the public execution surface* (Phase 0). Decide the public API
  posture (D-A), stop auto-deploying `:latest` unpinned, and make the trust
  path fail closed.
. *Make the verdict typed end to end* (Phase 1). The CLI and REST use
  `check()` → `ProverOutcome`, exit codes map to outcome classes, and no path
  reports a boolean.
. *Make the pipeline one function with a recorded policy* (Phase 1). There is
  one `verify_with_trust(state, policy)`. The policy, including any
  unsandboxed or unchecked downgrade, is recorded in every result.
. *Delete dead config or make it a compile error* (Phase 1). Every field of
  `ProverConfig` and `DispatchConfig` must be read. Remove crate-level
  `#![allow(dead_code)]` and ratchet it down.
. *Route every solver subprocess through one runner* (Phase 1, ratcheted). About
  about 100 backend source files call `Command::new` directly today. The target is
  zero outside the runner.
. *Implement two certificate checkers, or narrow the claim* (Phase 1, D-C).
  DRAT/LRAT and Alethe are the first two. Lean and Coq kernel acceptance is
  labelled as kernel acceptance, not as a certificate.
. *Consolidate CI from 35 workflow files into five lanes* (Phase 2). Use one
  aggregator as the required check so that path filtering is safe. Remove
  allow-fail jobs without an expiry, and make the required set match reality.
. *Externalise the 612 MB training corpus with a hashed manifest* (Phase 3,
  D-H). The working tree and checkouts shrink; provenance improves.
. *Generate status from sources, and keep one strategic document* (Phase 4).
  `ROADMAP.adoc` remains canonical. Stale status documents become generated
  or are deleted. Prover tiers are an attribute on the enum, not a table.
. *Hold Stage 5 (wire and coprocessor) until the verdict and trust types are
  frozen* (Phase 6, D-G). Do not parallelise untrusted execution (Chapel) before
  sandboxing is real, and do not freeze a wire schema before the types it
  encodes.

=== Three decisions that unblock most of the rest

[arabic]
. *D-A, public API posture.* Until this is decided, the highest-impact risk is
  open. *(E):* authentication plus sandboxed execution before further public
  traffic on the execution endpoints; read-only endpoints may stay public in
  the interim.
. *D-B, verdict break.* *(E):* make `check()` authoritative now, deprecate the
  boolean `verify_proof` path in the 2.x line, and remove it in the next major
  version. Consumers such as echidnabot and proof-burrower are not broken in
  the interim.
. *D-D, sandbox default.* *(E):* default-deny unsandboxed execution. It remains
  available in development only, and the provenance of each result records
  when it was used.

== Method and standard

=== The standard

The estate's standing methodology (standards#787, 2026-09-14) sets the lens for
choices between arms. Stated in the owner's terms, it is:

* *Elegance:* one mechanism per concern, and no special cases that exist only
  to make a test pass.
* *Correctness:* the claim is true by construction or by a gate that cannot be
  bypassed silently. A claim that depends on a hand-maintained statement is not
  correct.
* *Comprehensiveness:* every path that produces a result is covered, including
  the error paths and the deployment path.
* *Coherence:* the code, the documents, the CI, and the roadmap say the same
  thing, and each fact has one owner.

The choice is never made by effort, speed, or convenience. Where the cheap arm
and the elegant arm differ, the plan says so and recommends the elegant arm,
with the cost stated.

=== Working rule derived from it

Fix the generator, not the instance. For ECHIDNA the generator is the single
code path that produces a result, the single place where a gate is declared,
and the single source each status fact is derived from. A fix that edits one
result, one gate run, or one status sentence is a symptom patch and is
rejected in this plan unless it is a containment step (Phase 0).

=== 3.3 Architecture facts that drive the plan

* *Three `ProverKind` definitions.* The core enum in `crates/echidna-core` has
  141 variants. The GraphQL schema has the same set. The REST model in
  `src/interfaces/rest/models.rs` has its own 30-variant enum with different
  spellings (for example `Acl2` in REST and `ACL2` in core). There are no
  `From` conversions between them. The canonical count lives in
  `docs/PROVER_COUNT.adoc` and should be generated from the enum (Phase 4).
* *Dead-code lint is silenced in bulk.* About 150 files carry a file-level
  `#![allow(dead_code)]`, 103 of them under `provers/`. Unused trust modules
  therefore compile silently. There are also 33 item-level allows. DEBT C2 counts
  185 in total, which matches.
* *The verdict trait is lossy at its base.* `ProverBackend::verify_proof`
  returns `Result<bool>`. The default `check()` maps `Ok(false)` to
  `NoProofFound` and sends `Err` through `classify_anyhow_error`. Backends do
  not classify their tool's environment-failure messages, so most failures
  fall into the wrong class.
* *Default dispatch is permissive.* `DispatchConfig::default()` sets
  `min_trust = Level2`, `track_axioms = true`, and `generate_certificates = false`,
  and the integrity checker is `None`.
* *The repository is heavy for a source tree.* `training_data/` is 612 MB across
  152 tracked files. `models/` is about 26 MB. `.git` is about 99 MB. About 50
  `actions/checkout` steps each fetch the whole tree. The gitleaks configuration
  exempts `training_data/` from secret scanning.
* *Workflows are numerous and overlapping.* There are 35 workflow files plus
  `actions.lock`. Nine further workflow files sit under
  `echidna-playground/.github/workflows/` and never run, because GitHub reads
  only the repository-root `.github/`.

=== 3.4 Why the verdict fix is urgent (the learning-loop argument)

Stage 3 of the roadmap is defined as a learning loop in which the model
"improves from outcomes": prover outcomes feed strategy selection and,
eventually, training. If the CLI and the feedback path record
`SystemError` as "invalid", then a missing library path, a missing binary, or a
timeout is recorded as a property of the proof or of the strategy. The loop
then learns to avoid the prover, the library, or the strategy for reasons that
have nothing to do with the mathematics. This is an inference from the code
paths, not a measured result. The first test of Phase 1 should demonstrate it
or refute it on recorded data.

The same argument applies to the valence-shell feed (NW-2): a consumer that
treats environment errors as refutations will reject correct proofs whenever
the environment is misconfigured.

=== 4.2 Findings

*F-CI-1. Gates are advisory by design, and the required set is the wrong set.*
The live required set on `main` is eight contexts, in the
`echidna-proof-stack-branch` ruleset. The gates that failed most often in the
recent runs (governance, workflow lint, Hypatia) are not in it. PR #412 merged
with five failing check runs, none in that set. No live ruleset requires a
review, so a single maintainer can merge their own work, and two rulesets grant
the repository-admin bypass. This is not a process failure. It is the rule set
saying what it says, and the plan changes the rule set.

*F-CI-2. Green can mean "did not run".* Three mechanisms produce a green result
without the check having exercised anything: conditional pass-throughs,
skipped jobs, and allow-fail jobs. The conditional pass-through in
`idris2-abi-ci.yml` is deliberate, and it is sound only if its path detection is
exhaustive. === 4.3 The target CI design: one gate, five lanes

The elegant arm is to organise CI around _what a result must prove_, not around
_which tool produces the evidence_. That gives five lanes with one aggregator.

[cols="1,3,2", options="header"]
|===
| Lane | Contents | Trigger and budget

| *A. Merge gate* | `fmt`, `clippy -D warnings`, unit and integration tests, workflow lint,
  secret scan, server boot, FFI build, changed-path proof checks (Coq, Lean,
  Agda, Idris2 ABI). One aggregator job named as the single required check.
| Every pull request and push to `main`. Target: under 10 minutes median.

| *B. Security* | CodeQL (SAST), one Hypatia job, gitleaks, cargo-audit and cargo-deny in
  one job, Scorecard, ClusterFuzzLite. Findings go to SARIF and to the Security
  tab. Only the blocking tier (high and critical) fails a pull request.
| Pull request for changed paths; weekly full run.

| *C. Prover live* | Tier 1 and 2 live runs, tier 3 containers, tier 4 on demand, and
  the per-backend health matrix. Results published as artefacts, plus the
  generated status (Phase 4).
| Nightly (tiers 1–2), weekly (tier 3), manual (tier 4) within the budget set
  by D148.

| *D. Release* | SLSA provenance, image digest, SBOM, attestation. Deployment is by
  digest, never by `latest`.
| On release tag only.

| *E. Governance* | Documentation link check, status generation check, licence sweep,
  label and triage hygiene, ruleset drift check (live versus repository).
| Pull request on documentation paths and monthly.
|===

Design rules that make this coherent:

* *One aggregator.* A required check that always runs and reports the
  combined result of the lanes that apply. Path filtering inside lanes is then
  safe, and no pass-through shim is needed.
* *No allow-fail without an expiry.* Every `continue-on-error` names an issue
  and a date. After the date it becomes blocking or is removed.
* *Required set equals the set that matters.* The aggregator is the required
  check, and its definition is in the repository. Rulesets are exported to
  `.github/rulesets/` and a drift check (lane E) compares them with live state.
* *Reuse from the estate, not forks.* Coordinate with `hyperpolymath/standards`
  reusable workflows. Pin them by SHA. Do not copy them into the repository.

Targets (measured baseline, then target):

| Metric | Baseline (2026-10-09) | Target (end of Phase 2)

| Workflow files | 35 | 12 or fewer
| Runs per typical push (median per SHA) | about 20 | 6 or fewer
| Startup failure rate | 2.5% | 0% over 14 days
| Required check red on `main` for more than 14 days | yes (Security Scan) | no

=== Phase 1 — One verdict, one pipeline (weeks 1–4)

*Goal.* Make the three invariants true in code. Every result carries its
verdict class, its policy, and its evidence. Every gate is either required and
green or visibly not required. Every status claim is generated or dated.

Work:

* *1.1 Typed verdict end to end.* The CLI `verify` and `prove` commands call
  `check()` and receive `ProverOutcome`. Exit codes follow the class: 0 proved;
  1 no proof found; 2 invalid input; 3 unsupported feature; 4 environment or
  system error; 5 timeout. Backends classify the messages their tools emit for
  missing library paths, missing modules, and missing binaries as `SystemError`
  or `InvalidInput`. The first backends are the seven most used in the tests
  (Coq, Lean, Agda, Isabelle, Idris2, Z3, cvc5), chosen by usage data rather than
  by preference. The `echidna.prove.result/1` contract gains an additive `class`
  field. A breaking change requires a new contract version and is avoided here.
* *1.2 One pipeline.* A single `verify_with_trust(state, policy)` replaces the
  parallel paths. The policy names each requirement: integrity, sandbox,
  certificate, axiom tracking, minimum trust level. The default policy is strict.
  Any relaxation is a named policy, and its name is recorded in the result.
* *1.3 No dead configuration.* Every field of `ProverConfig` and `DispatchConfig`
  is read. Enforce this by destructuring the config in the constructor, so that
  an unread field is a compile error. `generate_certificates` stays only if 1.4
  wires it.
* *1.4 Certificates, scoped honestly (D-C).* Implement DRAT/LRAT checking for the
  SAT backends and Alethe checking for the SMT backends, through the external
  checkers (`drat-trim` and `carcara`). For Lean and Coq, the result is labelled
  *kernel acceptance*, which is a different and honest claim. Remove any other
  claimed format until it is built.
* *1.5 One sandboxed runner.* A single `ProverProcess` runner replaces the direct
  `Command::new` calls across the backends. The runner enforces the sandbox
  mode, timeout, environment scrubbing, a temporary directory, and output
  capture. The rollout is ratcheted: the count of raw `Command::new` in
  `provers/` goes down monotonically in CI, from about 100 files to zero. Each
  backend family is a separate pull request.
* *1.6 Dead-code ratchet.* Remove file-level `#![allow(dead_code)]`. Replace
  each with item-level allows that carry a tracking-issue comment. Delete
  modules that are genuinely unused, including the certificate stub if 1.4 does
  not use it.
* *1.7 One `ProverKind`.* The core enum is canonical. GraphQL and REST map to it
  through exhaustive `From` implementations, which makes a missing variant a
  compile error. The OpenAPI schema is generated from the canonical type.
* *1.8 Backend acceptance checklist.* A backend is accepted when it has
  classification tests for its environment failures, a live test, a tier
  attribute, an integrity entry, and a row in the generated status. This makes
  X4 concrete.
* *1.9 Test the learning-loop claim (section 3.4).* On recorded data, measure how
  many failures are environment-class under the old and new classifications.
  Record the result in the Phase 1 report, whichever way it falls.

Compatibility: `ProverBackend::verify_proof` keeps its signature in the 2.x
line. `check()` becomes authoritative and the boolean path is deprecated. This
avoids breaking echidnabot and proof-burrower in the interim (D-B). Confirm the
consumers' pinned versions before the deprecation is merged.

Exit criteria:

* On a deliberately broken Coq library path, `echidna verify` exits 4 with
  "environment" in the output.
* A placeholder integrity manifest yields `Unverified`, and the test is part of
  the merge gate.
* No direct `Command::new` remains in `provers/` outside the runner, or the
  ratchet metric is at its baseline and falling.
* No file-level `#![allow(dead_code)]` remains outside documented exceptions.
* One `ProverKind` definition exists, and a test fails if REST and core differ.
* At least one certificate checker runs in CI on a fixture, and its failure is
  visible.

== Non-goals and things to stop

* *No blanket baselines or allow-lists that make red green.* The 2026-09-25
  rule stands.
* *No pass-through shims presented as checks.* A check that cannot fail is not
  a check.
* *No new prover backends before Phase 1 exit.* Each new backend arrives with
  classification tests, a tier attribute, and an integrity entry (1.8).
* *No ROADMAP claim without a CI job or a measurement.* Describe intent in the
  roadmap as intent, with a date.
* *No configuration flags that are read nowhere.* Phase 1.3 makes this a
  compile error.
* *No new workflow files.* New checks go into a lane.
* *No Python, ReScript, or TypeScript,* per estate policy.
* *No parallel untrusted execution before sandboxing is real* (6.4).
* *No history rewrite* to shrink the repository (3.4).
