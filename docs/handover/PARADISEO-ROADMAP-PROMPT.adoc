== 2. Ground rules (from `CLAUDE.md`, `.claude/CLAUDE.md` and practice)

* *No Python anywhere in the repo* (estate ban). Use Rust for systems, Julia
  for data or batch, bash+jq for small CI scripts.
* SPDX header on every new file: `MPL-2.0` for code, `CC-BY-SA-4.0` for docs.
* Conventional commits (`feat(pareto): ...`, `docs(decisions): ...`), atomic.
* Docs are AsciiDoc (`.adoc`). `issues/*.md` is Markdown on purpose (GitHub bodies).
* Rust toolchain is pinned in `rust-toolchain.toml` (1.99.0, with clippy and rustfmt).
* `--features chapel` must still build when Chapel is absent.
* No new crates without a stated reason. ECH-01 needs none.
* Do not claim speed-ups, exactness or guarantees that a test does not back.
* `rust-ci.yml` runs on `pull_request` and on pushes to `main`/`master` only.
  A push to a feature branch alone runs no Rust CI. If you cannot run
  `cargo` locally, you need a draft PR (ask the owner first).
* Do not open PRs, file issues or create labels in other repos without the owner's say-so.

=== WP1: ECH-01: non-dominated sorting and exact hypervolume (`pareto.rs`)

Spec: `issues/echidna-01-pareto-moeo.md`. This is the best first coding task:
pure Rust, no new dependencies, one small module.

Current code (`src/rust/verification/pareto.rs`, 247 lines, `main@7fd369d`):

* `ProofObjective { proof_time_ms: u64, trust_level: TrustLevel, memory_bytes: u64, proof_steps: usize }`.
  `TrustLevel::value()` returns `u8` (1–5, `src/rust/verification/confidence.rs`).
* `ProofCandidate { .., is_pareto_optimal: bool }`. `ParetoFrontier::compute(&mut [ProofCandidate]) -> Vec<usize>`
  is O(n²) with a private `dominates`. `ParetoFrontier::weighted_rank(..)` uses inverse scaling.
* Existing tests: `test_single_candidate_is_pareto_optimal`, `test_dominated_candidate_excluded`,
  `test_tradeoff_candidates_both_on_frontier`, `test_three_way_frontier`,
  `test_weighted_rank`, `test_empty_candidates`. These must stay unchanged and pass.
* Consumers: `src/rust/agent/meta_controller.rs` (around lines 634–637:
  `compute`, then `weighted_rank(&candidates, 1.0, 0.5, 0.0, 0.0)`), re-exports in
  `src/rust/verification/mod.rs:55`, and `src/rust/verification/pareto_arbiter.rs`.
  Keep public signatures stable. Add new functions rather than changing old ones.

Step 1 (decision, record it in rustdoc and the PR): the hypervolume
*reference point*. Recommended: an explicit, caller-supplied reference point,
plus a helper that derives one from a candidate set (worst observed value × a
documented margin). Document that hypervolumes are comparable only under the
same reference point and transform.

Step 2: implement, as in the spec:

* One minimisation transform in one place: `[time, -trust, memory, steps]` as `f64`.
* `non_dominated_sort(&[ProofCandidate]) -> Vec<Vec<usize>>`. F₁ must equal `compute`'s result.
* `hypervolume(points, reference) -> f64`: exact. 2-D by sweep line; 3-D and 4-D
  by an exact slicing method (HSO or WFG style). Points not strictly better than the
  reference on every axis contribute 0. Monte Carlo is out of scope.
* `hypervolume_contribution(..)`: exclusive contribution per point.
* Tests: hand-computed 2-D/3-D fixtures (worked out on paper in the PR
  description); empty → 0.0; duplicates; point equal to reference; permutation
  invariance; `proptest` properties (adding a dominated point leaves HV unchanged,
  adding a non-dominated point never decreases it; no point in Fₖ dominates any
  point in Fⱼ for j < k).

Out of scope: adding these numbers to `echidna.prove.result/1` (see <<contract-hazard>>)
or to the dispatcher.

=== WP4: partial-progress field in `echidna.prove.result/1` (proposal; blocked)

PB-01 wants partial progress (for example `subgoals_remaining`). The hazard:

* echidna's contract says adding a field is compatible and consumers must
  ignore unknown fields (`docs/PROVE-RESULT-CONTRACT.adoc`, "Versioning").
  `echidna_core::prove_result::ProveResult::parse` tolerates unknown fields.
* proof-burrower's parser tolerates unknown fields (read-only at `be897dd`,
  `crates/burrower-core/src/echidna_contract.rs`; unverified).
* *echidnabot's own parser rejects them*: `src/dispatcher/prove_result.rs:79`
  has `#[serde(deny_unknown_fields)]` and a `rejects_unknown_fields` test
  (read-only at `ae52833`; unverified). Any new top-level field breaks echidnabot.

So: (1) file or fix in echidnabot first (tolerate unknown top-level fields, as the
contract requires); (2) only then add the field to echidna as `Option<_>` with
`skip_serializing_if = "Option::is_none"`, so existing golden JCS bytes
(`crates/echidna-core/src/prove_result.rs` `golden_jcs_bytes_for_every_status`,
`src/rust/prove_contract.rs` tests) stay unchanged when it is absent. Until (1)
is done, deliver only a written proposal.
